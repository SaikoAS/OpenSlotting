# Warehouse editor prototype

The **Warehouse editor / 3D-Editor** has three freely selectable modes: **Structure / Struktur**, **Zones / Zonen**, and **Locations / Lagerplätze**. The separate **3D analysis / 3D-Auswertung** reads the saved plan and current article-master data. Complete one level or rack while leaving others unfinished; there is no warehouse-wide completion gate.

## Structure

The **Add recipe / Rezept hinzufügen** dropdown groups recipes into **Racks / Regale**, **Wall modules / Wandmodule**, **Route modules / Fahrwegmodule**, **Building & access / Gebäude & Zugänge**, and **Routes & functional areas / Wege & Funktionsflächen**. Wall and route categories each offer a straight segment, corner, T-junction and crossroads. Recipes within each category are sorted alphabetically in the selected interface language. Native select groups retain keyboard navigation; category headings are not selectable recipes. The selected recipe survives editor redraws and mode changes. New rack types join the rack category automatically; future recipes appear under **Other recipes / Weitere Rezepte** until classified. Empty categories are omitted.

Build physical geometry first. New racks and levels have an Unassigned functional scope and **zero locations**. The three-step rack builder edits only type/name, bays/uprights, and levels/decks. Its front preview shows dimensions. Cancel or Escape leaves the saved layout unchanged; finishing is one undoable edit.

Pallet and shelf racks have 1–30 bays. One rack object represents a connected rack row with a **shared depth of 200–3,000 mm** for all bays and upright frames. Set this depth in the builder's first step or the rack's Structure properties; independent bay/frame depth controls are no longer offered. Changing the common depth updates beams, decks, markers, footprint and both views through the existing shared geometry. It is one undoable edit and retains physical, zone and location IDs and codes. Current locks, impact warnings and save-failure handling still apply.

Each bay retains its independent width and 1–12 levels. Each level has clear height, beam/shelf thickness, and an optional deck with its own thickness. Each upright retains independent width and height. New bays and frames inherit an existing common row depth; adding bays retains existing widths/heights and starts new bays with the first bay's level count. Stacks taller than an adjacent upright are rejected. All dimensions are millimeters.

Historical layouts with different bay/frame depths remain readable and unchanged on load or backup restore. The common depth field is initially empty and an explanation asks the user to choose a depth. Entering a value explicitly aligns every bay and frame, with undo available. The table builder requires a common depth before saving its draft; cancel leaves historical measurements untouched. Different-depth sections should be represented as separate rack objects.

Walls, gates, doors, emergency exits, aisles/roads, goods-in, and goods-out are physical objects with dimensions, coordinates, and rotation. Their floor-plan overlap never assigns Picking or Reserve use. These are planning symbols, not building or fire-safety validation.

### Rack passages

Select the rack and bay in Structure, then expand **Drive-through / Durchfahrt**. Enter the clear height below the first beam, retain or explicitly change the number of levels, and optionally associate an existing route. **Preview passage / Durchfahrt vorschauen** shows the proposed geometry and affected locations before **Apply / Änderungen übernehmen**. Cancel or Escape discards the candidate. Adjacent frames are raised only when the corresponding checkbox is selected; otherwise a stack exceeding a frame is rejected. Changing level count can remove locations, so review the impact warning. Surviving level, zone and location IDs and codes are retained.

The bay width determines the physical passage width. A passage does not disable collision checks or remove beams, posts or decks. Removing the passage designation removes only its route association; the adjusted physical heights remain. A route association is descriptive, not a motion constraint.

**Continue passage / Durchfahrt fortsetzen** selects a separate target rack and a target bay numbered from 1. The preview aligns the target rack's orientation and bay center across the row, retains row separation, and copies the bottom clear height and route association. Invalid target heights are rejected. Group both rack rows if they should subsequently move together.

### Connected structures and wall openings

**Add bay at start/end** extends a rack in a preview. At the start, the row origin moves so existing bays stay in their previous world positions. New parts receive fresh IDs and no locations. Existing common depth is inherited.

Under **Connect & align**, choose a compatible target and each free port. **Align ports automatically / Anschlüsse automatisch ausrichten** rotates the source so the chosen ports face each other, then places them together in a preview. Keeping the current direction or choosing a relative angle (0°, ±90° or 180°) remains available. The preview labels the ports. **Connect** persists a shared endpoint; **Align** only places the object once. Moving or rotating a member moves its connected assembly. Dimension changes reposition connected followers to retain their endpoints. **Disconnect** removes the selected object's connections without changing geometry. Connections cannot form cycles; closing a road circuit can be positioned with the magnet without adding the final persistent link. A locked stationary target is allowed; a change moving any locked member is refused.

In the floor plan, enable **Magnet** to see the selected module's numbered ports. Free, oppositely facing ports snap before the 100 mm grid, with the existing distance tolerance and hysteresis. Route modules connect only to routes of equal lane width. Wall junctions connect to walls, gates, doors or exits with equal thickness and elevation; set those dimensions explicitly. Rack connections remain separate from walls and routes. Occupied ports and members of the moving assembly are excluded from snapping. Magnetic placement does not persist a connection; use **Connect** when the parts should move together. Disconnect before changing a linked module's thickness or lane width to a different value.

### Connections over a distance

For two route modules (straight, corner, T or cross), or two wall modules, choose the target and both free ports under **Connect & align**, then use **Preview distance connection / Verbindung über Distanz vorschauen**. This operation keeps both existing objects and their assemblies in their current positions and orientations. It creates ordinary straight segments and corner recipes between the ports, persists both endpoint links and all intermediate links, and saves in one undoable action only after **Apply**. Cancel or Escape discards the entire candidate. Gates, doors and racks are not distance-connection end objects; connect them directly or add a wall segment first.

**Automatic** chooses the shortest suitable course among a bounded set of candidates, preferring fewer corners on equal length. **Straight only** refuses a bend or obstructed straight line. **First turn left/right** chooses the first turn relative to travel out of the source port. **Detour reserve** (100–10,000 mm, initially 500 mm) changes the offset candidates; it is not a vehicle safety margin or turning radius. The compiler tries at most 128 deduplicated orthogonal courses with offset coordinates near the endpoints and modeled obstacle extents. It is not a complete pathfinding solver; failure does not prove that no route exists. Choose another course/reserve or place intermediate modules explicitly when the bounded search fails.

Both ports need matching lane width or wall thickness and elevation, a separation of at least 100 mm, and parallel or perpendicular headings. The module grid may be rotated as a whole; arbitrary-angle legacy point paths are supported only when their port headings can be represented with the existing integer-degree module rotation. No existing part is rotated automatically by this operation. Corners retain their square hub and at least 100 mm per arm; short residuals are absorbed into an arm rather than saved as invalid tiny straight pieces. Straight pieces longer than 50,000 mm are split. Object and connection limits, existing locks and the 2 mm endpoint coincidence tolerance remain enforced. Persistent connection cycles remain unsupported, so the endpoint assemblies must be separate.

Each candidate is normalized and checked for self-overlap between nonadjacent modules and against actual modeled obstacle parts. Stationary endpoint contact is allowed at the first/last piece; other parts of those endpoint modules still obstruct an unsuitable course. Other existing route markings and goods-in/out overlays retain their existing overlap semantics; the compiler does not insert junctions or traffic connections into third-party routes. For routes, **Required width / Benötigte Breite** and **Required height / Benötigte Höhe** are also available directly in the distance-connection controls. They start with the largest known endpoint dimension or blank if neither endpoint specifies it. New pieces use the maximum of each supplied dimension and the known endpoint dimensions; a smaller entry cannot reduce an endpoint requirement. Side/height margins take the larger endpoint value, shown beside these controls. Required width plus both side margins must fit in the lane. The existing endpoints and their requirements remain unchanged.

Missing height no longer blocks every raised beam or deck. Instead, the search and layout check still reject solids intersecting the route's base plane, including posts, rack bases, walls and closed door leaves. Overhead clearance remains unknown; the preview and saved layout report **Not fully checked** when required dimensions are missing. Passage height is never substituted for vehicle height. Enter the actual vehicle/load dimensions to check the full vertical envelope from route elevation to required height plus margin. Wall pieces inherit the larger wall height and the source base elevation. Vehicle swept paths, loads and traffic suitability remain unassessed.

An existing rack does not have to be deleted to create a route through a bay. First configure the bay's passage if the beams need raising, then select compatible route ports and preview their connection. For example, a bay with 3,500 mm clear height admits a modeled 3,000 mm required height plus a 200 mm inherited height margin, provided the entire lane fits between the actual posts. A 3,400 mm requirement plus 200 mm margin is too high. The lane itself, including its corners, is checked at its full modeled width; increasing the detour reserve does not make a lane fit between posts. If the bounded search fails after encountering an obstacle, the message names the first encountered obstacle on a checked course and includes available/required height for a low beam or header. This does not prove all possible courses are blocked.

After applying, the generated modules remain individually editable, selectable and lockable with stable IDs. They use the existing connected-assembly rules: moving a member moves the assembly; resizing a member repositions connected followers. The compiler does not automatically reroute the connection after later edits. Disconnect links before independently moving an end object. Undo restores the pre-connection plan.

Under **Groups**, select at least two unlocked objects and a name. Each object belongs to at most one group. Groups translate and rotate together; **Ungroup** retains positions. Groups and endpoint connections are stored separately. A structure duplicate copies measurements and passage designation, with fresh IDs and no route association, group membership, endpoint links, zones classified for use, or locations.

For a straight wall segment, expand **Insert wall opening**, choose gate, door or emergency exit, and enter offset, width and height. Insert openings in straight segments connected to a junction, rather than into the junction hub or arm. The preview splits the wall into remaining sides and, where needed, an elevated lintel, and places the opening. The pieces are grouped automatically (or added to the wall's existing group). Existing outer endpoint connections are retained. Each remaining side must be at least 100 mm wide. Inserted doors start open; **Door open** toggles their leaf. Opening height includes the modeled top frame; the collision check reports its actual underside.

### Routes

Build new routes from **Route modules / Fahrwegmodule**. A corner has two ports, a T-junction three, and crossroads four. The same shapes are available under **Wall modules / Wandmodule**. Each junction is one physical object with one ID, lock, name and undoable edit; it is not a hidden group of independent pieces. Its position is the center of a square hub, whose side is the lane width or wall thickness. Arm lengths (100–24,000 mm) start at the hub edge and are independently editable. Initial arms point left/down for a corner, left/right/down for a T-junction, and left/right/down/up for crossroads; port numbers follow that order. Rotate the module as a whole for another orientation. Arms keep their port indexes as lengths change. The stored `width` is derived from the local bounding extent for junctions; it is not an editable arm length.

The top view, 3D view, picking and collision refinement use the hub and actual arm rectangles. Empty corner quadrants remain empty and cannot select the object. Bounding rectangles are used only for framing and broad-phase checks. The central square models the occupied junction area; curved corners, vehicle turning radii and swept paths are not calculated.

**Draw route / Fahrweg zeichnen** has been removed from the editor. Previously saved point paths are preserved, rendered and checked with their original segment/junction geometry; width, position, orientation and clearance requirements remain editable. They are not silently approximated as junction recipes. For a different path, build a replacement from modules, review any rack route associations, then explicitly delete the old object. Duplicating a legacy path retains that path.

Route properties separately specify required vehicle/envelope width and height, lateral margin **per side**, and height margin. The marking thickness is visual and is not the required clearance. Required dimensions remain empty for migrated or new standalone route modules until entered explicitly, independently for every module. Directly connecting routes does not copy requirements or establish traffic reachability; the distance compiler applies the endpoint requirements described above to its new pieces only. Missing dimensions produce **Not fully checked**, never a clearance approval. Model the required envelope including load; the software does not infer it from imported article data.

## Zones

Assign each rack level **Picking / Kommissionierung**, **Reserve**, or **Unassigned / Nicht zugewiesen**. The level list allows independent assignments at different heights within one rack. Apply a use to the selected bay or whole rack as a convenience; each level remains independently editable afterward. Assigning a zone does not create locations.

In the **Structure** mode's 3D view, pallet racks use blue upright frames (including their top and bottom frame members), orange beams, and light steel-gray decks. These illustrative component colors make adjacent rack parts easier to distinguish; they are not a manufacturer-specific or calibrated RAL specification. The legend labels each component in German or English. Selection and collision outlines remain visible over the component colors. Shelf racks retain their existing colors, with the functional legend also shown when they are present.

Green represents Picking, purple Reserve, and gray Unassigned. In **Zones** and **Locations**, beams and decks show the functional color even when there are no locations. The separate **3D analysis** defaults to the same component palette as Structure/3D. Its **Object colors / Objektfarben** and **Usage colors / Nutzungsfarben** buttons select the presentation; the legend follows the selected view. This choice is session-only and resets to object colors when changing workspace. Shelf racks retain their existing functional colors. In the floor plan (including Structure mode), each bay's functional bands represent its levels from bottom to top, not separate physical floor areas. Clicking a band or 3D beam/deck selects that level; bay/level selectors remain available. Location-code and article-match marker colors remain independent of the component palette. Switching modes changes presentation only; dimensions, zones, IDs, codes, collision checks, and saved workspace data are unaffected.

## Locations

Select a classified level and explicitly choose **0–4 locations**. Counts are independent per level. Existing IDs and codes survive expansion; only added subdivisions receive new IDs. Enter codes individually or fill empty codes in the selected level from a prefix in `PREFIX-BAY-LEVEL-POSITION` form with two-digit indices. The level action does not touch other levels. A separate rack action fills empty codes on existing eligible locations throughout the selected rack. Neither action creates locations or changes existing codes.

Codes are trimmed at their ends, case-sensitive, at most 80 characters, and unique workspace-wide. Leading zeros remain significant. Progress for the selected level shows its modeled state, functional use, and the number of coded locations. A scope can have an assigned use and no locations yet.

An Unassigned level explains the classification prerequisite and links directly to Zones. Its count controls are disabled. Locations retained after removing a classification remain visible and keep their IDs and codes. Migrated legacy locations additionally allow code editing before classification; resizing still requires a use assignment.

## Existing locations and safe edits

Changing dimensions, placement, functional use, subdivision counts, or existing codes prompts with the number of affected existing locations, codes, current article matches, and removed locations. Cancel retains the full saved layout. Confirmation applies one undoable edit. Geometry changes retain surviving physical IDs, zone IDs, location IDs, and codes; deleting a level/bay/object removes only its referenced zones and locations. Validation rejects orphaned references rather than silently dropping them. The warning counts current article-master matches, not inventory quantities.

**Duplicate structure** copies physical measurements with fresh part IDs, starts unlocked and Unassigned, and creates no locations. It preserves the original rack's assignments and codes. Undo/redo covers the last 20 saved edits within the current workspace. Mode changes are session state. Lock changes are saved outside history; undo/redo preserves current locks and refuses changes affecting a locked object's geometry, zones, or locations. Unlock before editing. A lock prevents accidental edits and is not an access-control mechanism.

## Views and layout checks

The bundled WebGL2 renderer uses a depth buffer and an offscreen color-ID pass for picking. In 3D, left drag rotates; right/middle drag or Shift+drag pans; the wheel zooms. Double-click or **Focus object** focuses the selected object. **Fit view** restores framing. **Walls** cycles solid/transparent/hidden without changing saved geometry. If WebGL2 is unavailable or lost, the top view remains available. Camera settings are session-only.

Route markings render as translucent top surfaces in the editor and read-only 3D analysis. A stencil coverage mask paints each visible route-covered sample only once, so overlapping straight pieces, junction arms and legacy segments retain the same opacity as a single piece. This avoids shaded side faces and darker overlap patterns. Rack occlusion still uses the depth buffer. The separate picking pass retains the original complete geometry and object references; selected-object outlines remain visible. Goods-in/out overlays and transparent walls retain their separate colors and transparency. WebGL2 is requested with a stencil buffer; if unavailable, the editor retains its top view. In the top view, all route rectangles share one fill operation, keeping overlap opacity uniform while preserving individual outlines, labels and selection. This is a display change only; no stored geometry, dimensions, connection, clearance or workspace format changes. Native Edge visual acceptance of the new coverage rendering remains pending.

### Scrolling, zoom and working space

- Wheel movements over the viewport zoom the editor; object lists, layout checks, properties, groups and builder tables scroll within their own regions. At their boundaries, scrolling does not transfer to the page. Wheel movements over a number input or select scroll the nearest available editor panel without changing the control's value or removing its focus. Explicit typing, arrow keys, spin buttons and selection remain available.
- Zoom handles pixel, line and page wheel units, scales continuously with movement, and redraws at most once per animation frame. Choose **Fine / Fein**, **Normal** or **Fast / Schnell** in **Zoom speed / Zoomtempo**. **− / +** zoom buttons and **Fit view / Einpassen** remain available during previews and route drawing. The displayed percentage is relative to the camera's fit/focus base; zoom is limited to 25–400%. Resizing preserves the camera state; Fit view recomputes framing for the available viewport.
- Focus the viewport by clicking it or reaching it with Tab. **+ / −** zoom, and **0** or **Home** fit the view. These shortcuts apply only to the focused viewport; editing fields retain their own keyboard behavior. **Ctrl+wheel**, including touchpad pinch gestures reported with Ctrl, remains available for browser zoom.
- OpenSlotting always fills the browser's available height with a rounded workspace frame beneath the banner and beside the navigation. The banner, navigation and compact privacy/version footer remain visible; the document itself does not scroll. Long forms and data scroll inside the active workspace view. Narrow windows use a horizontal navigation strip and internal view scrolling.
- On desktop, the editor toolbar, viewport and side panels share the remaining frame height. The viewport renders and picks at its actual displayed dimensions; lists and properties scroll separately. The separate 3D analysis places its search/details beside the viewport, with scrollable detail cards. Small windows and narrow layouts retain a usable viewport and reachable controls through internal scrolling.
- The former **Maximize editor / Editor maximieren** and **Restore editor / Editor verkleinern** toggle has been removed; there is no page-covering editor overlay. Escape cancels an open builder or preview, without changing the permanent workspace frame. Banner and navigation remain interactive during normal modeling.
- Redraws retain object-list and check-list scroll positions, selected objects, supported control focus and text selection. For the same object, properties retain their scroll position and open sections; a different object's properties begin at the top. Pending modeling-tool and count inputs are retained within the same selected scope. Changing scope or workspace does not carry those drafts into unrelated objects. Focus restoration does not automatically scroll the page.

Zoom speed, scroll positions and focus are session UI state; the workspace frame is a presentation rule. These do not change layout geometry, codes, saved workspace format or source data. The navigation and frame changes have received static syntax/whitespace checks only; native Edge mouse, touchpad, keyboard, browser-zoom and window-size acceptance remains pending.

In Structure's top view, drag an object to move it with 100 mm snapping, or use X/Z for exact coordinates. In Zones and Locations, the plan selects scopes and pans without moving geometry. Optional **Magnetic snap**, initially off, aligns nearby compatible endpoints before grid snapping, previews the target, and uses release hysteresis. It does not persist a connection; use the explicit Connect action for that. Wall corners are supported. Locked objects can be stationary targets. Placing a gate over an uncut wall does not create an opening; use Insert wall opening.

Collision checks first use rotated footprints to find candidates, then check the actual posts, beams, decks, frames, door leaves and solid bodies with their vertical extents. Rendering and checks share the same physical parts. Routes check their full modeled lane and junction area from their base elevation up to the required height plus margin; required width plus two lateral margins must fit inside the lane. Without height, solids intersecting the base plane still block, while overhead clearance remains incomplete. Overlapping route markings are permitted. Results distinguish blocked, too narrow, too low and incomplete. Select a reported part to focus it in 3D; the floor plan marks designated rack passages and their clear height. Goods-in/out remain intentional overlays and edge contact is permitted. Wall-wall and wall-gate/exit intersections retain their existing exemptions.

Warnings do not assess loads, stored goods, turning radii, traffic direction, pedestrian separation or statutory safety requirements. The geometry can be collision-free while a real vehicle cannot make the turn. This implementation has not yet received a new populated-data Edge acceptance or clearance-engine performance measurement; the linked earlier acceptance record is historical.

## Read-only article analysis

The separate analysis matches only current `location` values from imported **article-master** data to configured codes. It shows matched articles and unmatched codes. Click a location marker or search its exact code to inspect rack/bay/level/position, functional use, and matched articles. Multiple articles may share one location. Historical order-line locations do not determine occupancy. The analysis has no layout save controls and does not show unreliable stock-by-location quantities.

## Storage, migration, and limits

Workspace schema **16** stores layout schema **4**: physical `objects`, level-reference `zones`, explicit `locations`, `groups`, and `connections`. Migrating a populated layout schema 1 moves nested `levels[].positions[]` into the location collection, preserving every position ID and code. Those migrated scopes are Unassigned; no Picking/Reserve classification is inferred. Layout 2 retains its existing uses and adds empty groups/connections, no passage designation, and unknown route requirements. Layout 3 retains all of its geometry, point paths, connections, groups, passages, uses and codes; no junctions are inferred. Current article-master matching therefore remains exact. Workspaces predating a warehouse plan receive an empty schema-4 plan. Applications supporting workspace schema 15 or earlier cannot read schema-16 workspaces; keep a pre-update backup for returning to an older application.

Layout changes use metadata-only, revision-checked IndexedDB writes and do not rewrite CSV bytes, normalized row chunks, or article-registry chunks. Existing workspace backups include the complete plan and migrate legacy backups during restore. The database version remains 3. The plan is limited to 150 physical objects and 5,000 logical locations.

Both app views use bundled assets through the standard Python loopback start. No remote asset or additional package is required. Portable Mode remains paused; see [portable-mode-paused.md](portable-mode-paused.md). Existing Portable workspaces must be exported with their previous application and restored at the fixed localhost origin. Browser storage remains origin-specific.

For automated and manual acceptance, see [warehouse workflow acceptance](acceptance-warehouse-workflow.md).
