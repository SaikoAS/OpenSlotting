# Warehouse editor prototype

The editor is available from the **Warehouse 3D / Lager 3D** item in an opened workspace. It stores a parametric plan in that workspace's IndexedDB metadata and includes it in the existing workspace backup. The same local assets run through the standard loopback start and by opening `index.html` directly through `file:///`; no network asset or additional service is required.

## Recipes and dimensions

- Choosing a pallet or shelf rack now opens a three-step rack builder. **Basics** sets the type, name, starting bay count, and initial number of levels. **Bays and uprights** provides editable tables for each bay's width, depth, and level count and for each upright's width, depth, and height. **Levels and preview** provides a table for every level in the selected bay, including clear height, thickness, position count, optional deck, and deck thickness. Switch bays to edit their levels independently. A schematic front view and dimension/position totals update as the draft changes.
- The builder keeps a separate draft: **Cancel** or Escape leaves the layout unchanged, while **Add rack** saves the completed rack as one undoable edit. An existing unlocked rack can be opened through **Edit structure in table**. Existing bay, level, upright, and position IDs and codes remain intact when their parts remain; reducing counts warns before coded positions are removed. Validation of the full draft, including upright height and the overall position limit, must pass before applying it. Locked racks remain inspectable and must be unlocked before editing.
- **Pallet rack** and **shelf rack** have 1–30 bays. Every bay has its own width, depth, and independently editable count of 1–12 levels. Each level has its own clear height, beam or shelf thickness, optional deck with its own thickness, and independently editable count of 1–4 positions. Each upright has its own width, depth, and height. Changing the rack's bay count retains the differing level and position counts in existing bays. New bays start with the first bay's level count and first level's position count; they receive new IDs and empty codes.
- **Wall, gate, door, emergency exit, aisle/road, goods-in, and goods-out** are dimensioned objects that can be positioned and rotated. Gates, doors, and emergency exits are drawn as frames; the door also has a leaf. Aisles and zones are flat surfaces. These are planning symbols, not safety or building-code verification.
- All dimensions and coordinates are in millimeters. X and Z define the floor plane; height is vertical. The 3D view supports drag to rotate, wheel to zoom, and click to select a rack or position. In the top view, drag an object footprint to move it with 100 mm snapping; drag empty space to pan. The numeric X/Z fields remain available for exact coordinates. Fitting the view recenters the whole plan.
- The 3D view uses the bundled `warehouse-webgl.js` WebGL2 renderer with a depth buffer, so racks, walls, and positions cover one another according to their actual depth. Clicking uses an offscreen color-ID pass with the same depth geometry. The **Walls** control cycles between solid, transparent, and hidden walls in 3D; it changes only the view, never the saved plan. Transparent walls are a visual cutaway and may still overlap one another visually. The top view remains a separate 2D canvas. If WebGL2 is unavailable or its context is lost, the editor shows the top view and disables the 3D button until the context recovers.
- **Magnetic snap** is an optional toolbar switch, off when the editor starts. In the top view, dragging a wall, gate, door, or emergency exit near a compatible end of another such object aligns their centerline endpoints exactly. Wall-to-wall connections can turn corners; gates, doors, and exits connect in a straight line. A highlighted endpoint and target name preview the connection. Snapping uses a screen-based distance capped at 50–300 mm, with a larger release distance for the active target to reduce jitter. A magnetic connection takes precedence over the 100 mm grid; otherwise the grid applies. Locked objects can be connection targets but cannot be moved. Switching views or reloading does not change saved geometry; the switch itself is a session preference and resets to off on reload. The drag is one undoable layout edit. Doors and gates placed into a continuous wall do not automatically cut an opening; arrange wall segments around them. A door overlapping an uncut wall produces a collision warning.
- The selected object can be rotated left or right by 90° or given an exact angle in the properties panel. Duplicating a rack retains its measurements but gives every part and position a new ID; the duplicate's location codes start empty. Undo and redo cover the last 20 saved layout edits in the current editor session, including placement, rotation, duplication, dimensions, codes, and deletion. New edits clear the redo history. The history resets when another workspace is opened or the page reloads.
- Every object has a **Lock / Unlock** control in its properties panel. Locked objects remain selectable and visible; rack bays, levels, positions, codes, and imported article matches can still be inspected. Moving, editing dimensions or codes, generating codes, rotating, duplicating, and deleting the object are disabled until it is unlocked. The object list and floor plan mark locks. Undo and redo preserve the current lock state and refuse a history step that would change or remove a locked object; unlock it first. Lock changes themselves are not history steps, so undo cannot accidentally unlock an object. Duplicates start unlocked. The lock is stored with the layout and included in workspace backups; older layouts load unlocked. This is protection against accidental edits, not an access-control mechanism.
- Layout checks warn when rotated floor footprints overlap across racks and obstacles, or when a rack or wall obstructs an aisle. The summary and object list mark affected objects, and the warning list can select either object in the floor plan. A shared edge is not a collision. Goods-in and goods-out zones are overlays; wall-to-wall joints, wall-to-gate/exit openings, and aisle-to-gate/exit crossings are intentionally excluded. Warnings do not block saving, and they do not check clearance distances, vertical separation, or building and fire safety requirements.
- Generated geometry is derived from the saved measurements. Each rack, bay, upright, level, and position has a stable ID. Increasing counts retains existing IDs and codes. Reducing the count of bays, levels in a bay, or positions in a level warns before coded positions are removed. A level stack exceeding an adjacent upright blocks that edit.

## Location codes and imported articles

Each position can hold one location code. Codes can be entered individually or generated into empty positions from a prefix in `PREFIX-BAY-LEVEL-POSITION` form, with two-digit numbers. Codes are trimmed at their ends, case-sensitive, and must be unique in a workspace; leading zeros remain significant.

The overlay uses only the current `location` from imported **article-master** data. It matches that code exactly to a modeled position, shows matched article counts, and lists the first unmatched article locations for review. Clicking a position marker in 3D or searching its exact code selects it and shows its rack, bay, level, position number, and matched articles. Multiple articles may refer to the same modeled position. Historical `location` values from order lines are not treated as current occupancy. The current import does not contain reliable quantity-by-position inventory data, so the prototype does not show stock quantities.

## Storage and current limits

Schema version `12` adds an empty plan to earlier workspaces during validated activation. Layout edits, including completed top-view drags, use metadata-only revision-checked writes, so they do not rewrite original CSV bytes or normalized row chunks. Backup export and restore include the plan. The plan is limited to 150 objects and 5,000 positions; this first version is intended for layout and code validation rather than building-code assessment or large-facility CAD editing. Overlapping objects are allowed with the warnings described above.

The renderer is bundled with the other local files for both direct `file:///` use and the loopback localhost launcher. It sends no geometry or workspace data to a service. Browser storage still belongs to the origin: direct file use and localhost use keep separate IndexedDB workspaces, so moving an existing plan between them requires workspace backup export and restore.
